# 风险决策表 v0

> 规则：高风险项不自决，提供 A/B 方案、推荐项与影响面。

## R1 规约承载位置

- **问题**：规约写入 `README.md` 还是拆分 `CONTRIBUTING.md`。
- 方案 A：仅 `README.md` 增《项目规约》章节。
- 方案 B：`CONTRIBUTING.md` 承载完整规约，`README.md` 仅链接摘要。
- **推荐**：B（降低 README 噪音、便于迭代）。
- 影响：文档组织，不影响运行时。

## R2 死文件与产物删除标准

- **问题**：`Package/`、`bin/*.exe`、日志、`*.wcx`、大样本是否继续入库。
- 方案 A：保留现状，只新增忽略规则。
- 方案 B：建立白名单，仅保留源与必要样本，历史产物从追踪移除。
- **推荐**：B（仓库体积、审查质量与 CI 稳定性明显更优）。
- 影响：历史工作流变化，需团队共识与迁移说明。

## R3 实体中心路径

- **问题**：是否采用 `src/core/entities/` 作为全局实体权威定义中心。
- 方案 A：保持 Python `gui.models`（历史 `gui.domain.models`）与 C++ 侧并存，逐步对齐。
- 方案 B：建立实体中心并分阶段迁移适配层。
- **推荐**：B（长期可维护性更优），但需阶段化实施。
- 影响：中高风险；涉及跨 Python/C++ 契约与序列化边界。

## R4 大规模格式化策略

- **问题**：是否允许单 MR 全仓格式化。
- 方案 A：允许一次性格式化。
- 方案 B：禁止一次性格式化，按模块与业务改动绑定。
- **推荐**：B（可审性高，回溯成本低）。
- 影响：开发节奏与审查体验。

## R5 公共 API 重命名窗口

- **问题**：例如 `dp_depth` 在算法间语义冲突，是否立即统一重命名。
- 方案 A：立即改名并同步所有调用点。
- 方案 B：先建立别名兼容层与弃用期，再分阶段切换。
- **推荐**：B（回归风险可控）。
- 影响：中风险；涉及 pybind、GUI 配置、已有压缩记录兼容。

## R6 打包路径治理

- **问题**：`run.bat` 对构建产物路径耦合高，是否立刻重写。
- 方案 A：保持脚本，先补注释与探测。
- 方案 B：改成统一 Python/PowerShell 构建入口并参数化。
- **推荐**：A -> B 两阶段（先稳，再改）。
- 影响：中风险；直接影响发布路径。
