在这次调试对话里，我没有说过「流式和非流式必然会有压缩率差异」。

实际立场更接近下面这样：

1. 项目验收标准：要求一致，不是接受差异
docs/debug_plan.md 写得很明确：

条件 A：同算法、同参数下，流式与非流式压缩输出要逐字节一致（不是只比压缩率）。
条件 B：解压结果要与原文件一致。
两条都满足才算 PASS。也就是说，设计预期是 parity（比特级一致），而不是「流式本来就会更差/更好」。

2. 这次对话里主要在修什么
我们修的是 解压 CRC 错、选错解压器（Inflate vs Inflate3HM）、位流写法、DP 回溯读盘错位 等正确性问题，目标是：

流式/非流式都能 正确解压；
在 debug 计划里满足 A + B。
test_dpflate_3hm_stream 主要验证的是 流式压 → 流式解 → 与原文件一致，并没有把「流式压缩率必然不同于非流式」当作结论。

3. 压缩率差异在仓库里被当成 异常/待查，不是定理
你们自己的材料里，差异是 现象/缺陷，例如：

docs/prompts(important).md：LZSS 流式与非流式结果有差异；DPFlate 流式与非流式压缩率不一致等；
设计讨论（如 docs/理解LZDP和DPFLATE流式压缩设计.md）里还有观点：按分块 DP + 滑动窗口衔接做对，不应出现流式/非流式不一致——这和「肯定会差」是相反的。
所以若你记得有人说过「肯定会差」，更可能来自：

观察到 GUI/旧实现里 dpflate、lzss 等 确实差过（当 bug 报）；
或 一般性工程经验：分块边界、不同代码路径、启发式 DP 等 可能导致 差异——那是 可能原因，不是「必然」。
4. 什么时候「可以」有差异（理论上的可能，不是本项目的验收目标）
在实现不完整或故意用不同策略时，流式和非流式可能压缩率不同，例如：

分块处 match/DP 窗口衔接不对；
流式走 Out-of-Core + 临时文件，非流式整段 compress_dp；
参数/路径不一致（GUI 里 compressed_path 残留导致解的是旧流式文件等）。
这些是 应修到一致 的情况，不是「流式天生就该更差」。

简短结论：

我说过/计划里写的：应尽量 比特级一致 + 解压正确。
我没说过：流式和非流式 肯定会 压缩率不同。
若你看到 0.3% 这类差别：在你们的 debug 语境里应视为 parity 失败或路径/参数不一致，需要对比实验（test_lzdp_memory_streaming_parity、逐字节比 .wcx payload 等），而不是当成正常现象。
