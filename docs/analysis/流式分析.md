## 工程化结论（用于修正旧流式模块）

这次反思的关键不是“分块大小如何选”，而是**不同阶段的处理单元不同**：

| 阶段 | 处理单元 | 边界风险 | 必须保存的接力状态 |
|------|----------|----------|--------------------|
| dpfoward / collect | 原始 `uint8_t` | search window / lookahead 不完整导致 token 不一致 | `input_buffer_`、`window_abs_pos`、`current_i`、两块 DP frontier |
| backtrack | 固定临时记录 `DpLink` / `Triple` | chunk 末尾不足一条记录；`cur` 按 predecessor 跳转，不等于顺序扫描 | record carry、`cur`、temp B 写入位置、`total_tokens` |
| count_freq | token 记录 | 3HfMTree 的 literal-run 跨 chunk 被拆断 | record carry、literal-run length |
| emit | 最终编码 bitstream | 未满 8 bit 的尾巴丢失或提前补 0 | `BitWriter` pending bits、literal-run buffer、emit token index |

### 1. 临时写入和编码写入必须分离

临时写入用于中间文件，不应该使用最终编码格式。目标是固定字节 record，方便按下标定位和跨 chunk 解析：

```cpp
struct TempTokenRecord {
    uint16_t length;  // 0 = literal
    uint16_t offset;  // literal 时存 byte，match 时存 offset
};
```

编码写入才使用 bit-level 规则。只有最终压缩 bitstream 需要处理“不满 8 bit”的 pending bits；temp A / temp B 不应该引入 bit 残留问题。

### 2. 回溯不是普通反向顺序读

DP 回溯的真实循环是：

```cpp
cur = total_in_len;
while (cur > 0) {
    link = tempA.read_record(cur);
    tempB.append(link);            // 这里写出的是反序 token
    cur -= link.length == 0 ? 1 : link.length;
}
```

所以 temp A 必须能按 `cur` 直接定位；temp B 必须能在 emit 阶段逆向读取，恢复正向 token 序。

### 3. literal-run 是跨块语义状态

non-flag LZDP 和 3HfMTree 都不能把 literal 当成独立 token 逐个编码。正确逻辑是：

```cpp
if literal:
    literal_run.push(byte)
else:
    flush_literal_run()
    write_match()
end:
    flush_literal_run()
```

`literal_run` 不能是函数局部变量，因为 `need_output`、chunk 结束或状态机让出后还要继续。

### 4. DP 更新条件必须使用 cost

流式和内存 DP 都要用同一个 cost 语义比较候选，而不是比较 `token_count`。尤其 non-flag literal-run 下，多个 literal 合并成一个 run header，代价不是“literal 数 × 单 token 成本”。

这里需要注意 C++ 优先级：

```cpp
size_t maxlen = (size_t{1} << config_.encoding.length_bits) - 1;
```

不要写成 `size_t{1} << config_.encoding.length_bits - 1`，否则含义会变成 `1 << (bits - 1)`。
