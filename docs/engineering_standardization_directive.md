# 工程标准化治理 — 指示型任务书

> **用途**：本文档作为对本仓库进行架构与工程规范治理的**唯一任务说明**。执行者（人或自动化代理）应严格按本文档的边界、标准与交付物执行；需求方通过「阶段闸门」确认后再进入下一阶段。

---

## 1. 角色与授权

- **执行者**：本项目的全权架构治理执行者，拥有跨模块、跨目录修改权限。
- **需求方**：保留对**高风险项**与**阶段切换**的最终拍板权。
- **工作方式**：执行者**不需要**需求方逐条指导实现细节，但必须按本文档交付**可验收产物**；凡无法 100% 确认安全的改动，**必须标注**并提交需求方决策。

---

## 2. 问题现状（背景共识）

项目因长期缺乏统一规约，已出现或可预见以下症状：

| 类型 | 表现 |
|------|------|
| 重复实现 | 同一逻辑多处拷贝，改一处漏一处 |
| 概念分裂 | 同一业务概念不同命名、不同数据结构，模块间靠猜测对接 |
| 目录语义弱 | 组织原则不明，新人难以定位 |
| 构建与打包 | 脚本与配置堆叠、「祖传」路径与环境假设，冗余依赖与死代码 |
| 缺少门禁 | 无成文规约与自动化检查，结构易被随意破坏 |

---

## 3. 目标终态（验收口径）

在不破坏**现有可观测功能**（编译、打包、核心压缩/解压路径、GUI 主流程）的前提下，达到：

> **任何人 clone 仓库后，看目录名能判断归属，看文件名能判断职责，看函数签名能判断用法，尽量不依赖口头知识。**

「不破坏」的最低标准：**每个可合并阶段结束时，工程须能完整编译；若存在打包/发布路径，须能完成一次标准打包；主程序可启动并完成冒烟路径**（具体命令在阶段 0 写入《构建基线》）。

---

## 4. 必须覆盖的六个维度

### 4.1 文件与目录结构

- 建立**有文字说明的**目录树原则（例如：`algorithm` / `core` / `bindings` / `gui` 的职责边界）。
- 清理**死文件**与**名不副实**文件；删除须有依据（引用扫描或构建图），并在《技术债审计报告》中登记。

### 4.2 命名体系

- 制定全工程适用的**命名规则**（C++ / Python / 配置键名）。
- 输出《**命名正名词典**》：旧名 → 新名 → 适用范围；存疑项单列「待决」，不得强行合并。

### 4.3 代码架构

- 斩断**跨领域非法引用**（例如 UI 直接依赖实现细节、算法层反向依赖 GUI 等 —— 以审计为准）。
- 消除**可证实的重复代码**；抽取或内联须有《重复代码消除清单》记录及理由。
- 明确**单向依赖方向**（建议：自上而下由「入口 / 应用」→「领域服务」→「算法与基础设施」），并在规约中成文。

### 4.4 模块接口契约

- 建立**全局唯一的实体定义中心**（默认物理路径：`src/core/entities/`，若变更须在阶段 0 风险表中批准并更新映射表）。
- **收敛**跨模块重复的类型定义与「同一概念多种结构」问题。
- **统一**对外 API 的返回/错误表达（在契约层约定，而非各处临时结构）。

### 4.5 打包与构建系统

- 梳理环境变量、工作目录假设、产物输出路径。
- **构建与打包配置文件须带逐行或逐块注释**（说明意图、依赖、可改参数）。
- 消除**重复打包步骤**与无效缓存逻辑；输出**整改前后产物体积对比**表。

### 4.6 项目规约与自动化

- 制定并落地**工程规约**（目录、命名、依赖、提交、PR 体积与格式策略）。
- 配置 **CI 中的 Lint / 静态检查**（及本地等价命令），使明显违反规约的变更可被机器拦截。

---

## 5. 硬性约束（违反即视为未交付）

1. **分阶段可验收**：每一阶段结束须满足第 3 节「最低标准」；否则该阶段不得标为完成。
2. **高风险不得自决**：凡执行者无法 100% 确认安全的行为（大规模移动路径、删除疑似死文件、改变公共 API 语义），须在《风险决策表》中列出 **选项 A/B、推荐项、影响面**，交需求方书面确认。
3. **提交可追溯**：每一次合并到主线的提交信息须写清：**改了什么、为什么这样改**；禁止巨型「仅格式化」与业务重构混在同一提交（除非需求方明确批准单 MR 格式化策略）。
4. **闸门**：在未获需求方对**执行计划（见第 7 节）**及**阶段 0 风险表**书面确认前，**不得**进行会大规模移动源文件或改变公共 API 的提交。

## 6. 交付物清单（全部完成即视为本任务闭环）

| 序号 | 交付物 | 最低要求 |
|------|--------|----------|
| 1 | 《技术债审计报告》 | 重复代码、命名冲突、非法/可疑依赖；**带文件与行号或等价定位** |
| 2 | 《旧文件路径 → 新文件路径映射表》 | 每次搬迁目录须更新；含「未搬迁仅重命名」记录 |
| 3 | 《命名正名词典》 | 旧名、新名、适用范围、废弃时间表（若有） |
| 4 | 《重复代码消除清单》 | 每处：抽取/内联/保留理由、关联 PR 或提交 |
| 5 | `src/core/entities/`（或经批准的路径） | 核心实体**唯一**权威定义；须有 README 或索引说明纳入规则 |
| 6 | 构建与打包配置（注释版）+ 体积对比 | 整改前后产物大小、主要模块占比（可粗粒度） |
| 7 | `README.md` 中的《项目规约》章节 | 或 `CONTRIBUTING.md` + README 链接 —— **须在阶段 0 与需求方约定形式** |
| 8 | CI Lint 配置 | 含本地运行方式；从「仅警告」到「门禁」须有分步说明 |

## 7. 执行计划（分阶段 — 动手改代码前须获确认）

### 阶段 0 — 基线与只读审计

- **行为**：不改变业务路径语义；允许新增文档、脚本只读扫描结果。
- **产出**：《技术债审计报告》v0；当前 CMake / PyInstaller / Python 入口的《构建基线》一页；《风险决策表》v0。
- **验收**：仓库行为与整改前一致；仅增加审计类文件（路径在阶段 0 末与需求方确认）。

### 阶段 1 — 规约与词典冻结

- **产出**：《命名正名词典》v1（仅收录证据充分项）；《项目规约》草案；Lint 工具链选型说明。
- **验收**：CI 可先「警告不失败」或仅文档；**禁止**单 MR 内全仓库无意义格式化导致不可审。

### 阶段 2 — 实体中心与接口契约

- **产出**：实体目录首批迁入；《重复代码消除清单》首批。
- **验收**：全量编译 + 现有测试/约定冒烟通过。

### 阶段 3 — 目录与文件归位

- **产出**：《路径映射表》定稿；分模块 MR（如仅 `algorithm`、仅 `gui`）。
- **验收**：无悬挂 include/import；文档与脚本中的路径已更新。

### 阶段 4 — 构建与打包治理

- **产出**：注释版构建/打包配置；《产物体积对比》。
- **验收**：干净环境一次完整构建与打包成功；对比表可复核。

### 阶段 5 — Lint 收紧与规约定稿

- **产出**：CI 从警告到门禁的分批策略；README《项目规约》定稿。
- **验收**：示例「违规提交」应在 CI 失败（规约中可附最小反例）。

---

## 8. 需求方须提前拍板的典型风险（阶段 0 须展开）

- README 规约章节 vs 独立 `CONTRIBUTING.md` 及与外部链接的关系。
- `src/core/entities/` 与 Python `gui.core.models`、C++ `ICompressor` 等的边界，避免双世界循环依赖。
- 是否允许「单 MR 超大格式化」及与可审性的权衡。
- 死文件删除标准（日志、二进制、用户生成物是否纳入版本库）。
- PyInstaller / CI 缓存策略与「每次清缓存」对构建时间的影响。
